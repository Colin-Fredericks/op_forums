            The current platform has much less hardcoded content than previous editions. Whether this scratches your particular itch only time will tell. These days, we try to hardcode as few assumptions as possible, but at times, it is hard to notice - and at certain points, "just hardcode it" is a very reasonable decision: It is an order of magnitude easier than writing a fully generic rules engine for variations that we do not yet know about.
            Even though, we'll still prefer pull requests via github over raw files sent in by email.

            I have extracted a very technical sample of the extent of configuration for character types below.

            The type definition. You can remove or exchange each of the models with no harm done, as long as no other models depend on them.
            Free raises for all abilities? Remove the line. Different starting health levels? Make a new template and change the definition. (See below)
            Code:
            { characterType: Solar; template: Lawgiver; models: { Description:'', Points: SolarPoints, Concept: SolarCastes, SpiritualTraits:SolarSpiritualTraits, SpiritualPoints:SolarSpiritualPoints, Abilities: SolarAbilities, AbilitiesPoints: SolarAbilityPoints, Attributes: DefaultAttributes, AttributePoints: SolarAttributePoints, EssencePool: SolarEssencePool, Health: SolarHealth, ...more of the same... } }
            And this is the health definition for Solars. Please say this is cool.
            Code:
            { levels: [-0,-1,-1,-2,-2,-4,Incapacitated] }
            As a more complex example, this is the definition of "Default Attributes":
            Code:
            { groups: [ { id: "Physical", traits: ["Strength", "Dexterity", "Stamina"] }, { id: "Social", traits: ["Charisma", "Manipulation", "Appearance"] }, { id: "Mental", traits: ["Perception", "Intelligence", "Wits"] } ]; standard: { startValue: 1; minimumValue = 1; modificationType: "RaiseOnly"; limitation: { type: "Essence" } } }
            Last edited by urskr; 04-19-2015, 03:16 AM. Reason: You can now change attributes.

                                                        04-10-2015, 09:17 AM
                                                        Originally posted by urskr View Post

                                                        We currently don't plan to re-write the sheet encoding, so I don't think we'll go there. As always, contributions are welcome, but in this case I'd love to know where you see the advantage over what we currently do: building the vectors and text elements for the PDF in Java code based on the character's traits and properties.

                                                        It's Exalted.
                                                        A boring, but useful example is a tax form. You have lots of fillable fields to type numbers and text into and depending on the settings of the document (Acrobat is .. weird about it's permission sets), you can save the text you typed in which gets outputted as a .fdf file. All the data in this fdf file relates to the names of fields in the pdf rather than positioning within pdf document. The PDF determines where that field is drawn and the FDF determines what the contents of that editable field is. The idea in this case would be to come up with a PDF agnostic FDF output. Then, so long as the field mappings were done correctly, you could have any number of PDF documents. They all might have the "Name" and "Str Attribute" fields, but where and how they're drawn depends on the individual PDF. What this effectively does is allow you to template the final printout without having to worry about drawing different character sheets in your own software. All you'd need to worry about is the encoded form data that plugs into various other character sheet PDF documents.


                                                        Lets say someone gifted in design comes up with a fantastic new character sheet layout. What you could do is take their PDF, use PDF editing software to add the proper fields in the proper placement and now it's all set utilize the output you'd already be generating for other PDF templates, requiring no change in Anethema's code to accommodate the new layout.
